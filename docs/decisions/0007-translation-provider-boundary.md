# 0007：翻译服务使用应用层 provider 边界

日期：2026-08-05

## 背景

桌面 MVP 最初直接在 `LocalWorkspaceService` 中读取 DeepL 密钥并调用 DeepL 适配器，界面状态和操作文案也写死为 DeepL。这能快速验证日文到简体中文的真实流程，但继续接入 Google Translate 或 LLM 时会把凭据、请求格式、模型名称和错误处理扩散到应用层与 UI。

字幕翻译还有一项不可交给具体服务决定的约束：字幕段的稳定 ID、顺序和时间轴必须保持不变，全部结果应在一次 SQLite 事务中写入。不同 provider 可以使用相邻字幕作为上下文，但不能自行改变结果与输入的对应关系。

## 决定

- 在应用层定义 `TranslationProvider`，接收语言选项、按顺序排列的文本和可选共享上下文。
- provider 必须按输入顺序返回一一对应的结果；应用服务在写入前校验结果数量，并继续负责稳定段 ID、原文并发校验和 SQLite 原子事务。
- provider 通过通用状态结构暴露稳定 ID、显示名称、是否已配置、可选模型和配置提示。状态不得包含密钥。
- DeepL 成为基础设施适配器，并保持决策 0004 的行为：每段仍是独立 `text`，批量请求携带当前 SQLite 工作区生成的局部 `context`。
- Tauri 组合根选择并注入 provider；桌面 UI 只显示当前 provider 的通用状态和名称，不再写死 DeepL。
- 当前产品默认仍为 DeepL。CLI 的 `DEEPL_AUTH_KEY` 参数保留为兼容入口，直到桌面设置流程取代环境变量。

## 后果

- Google Translate 或 LLM 翻译可以通过新适配器接入，不需要修改字幕持久化与桌面操作流程。
- 对 LLM 来说，结构化输出解析、逐段一一对应和模型选择属于适配器职责；不能让自由文本响应直接写入工作区。
- provider 抽象本身不解决跨字幕段的语法断裂。共享上下文可以消歧，但不会把多个独立输入合并成一个翻译单元。若以后要改善句子被 ASR 切断的问题，需要单独设计“翻译单元合并与稳定映射”，并用真实字幕质量回归验证。
- 在接入第二个真实 provider 前，仍需确定设置界面、macOS Keychain、模型/端点配置，以及在翻译结果中记录 provider 与模型来源的 schema。
